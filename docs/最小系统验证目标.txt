最小系统验证目标
这个 MVP 只需要验证 5 件事：
1.能指定一个本地项目目录
2.能扫描该项目里的 Python 文件
3.能读取该项目的 Git 提交记录
4.能生成节点和关系
5.能在前端无限画布上显示科技树式节点，并区分新旧提交
不需要一开始就做：
?完整权限管理
?多项目复杂管理
?真实测试数据接入
?完整状态聚合
?生产部署
?复杂类型系统

可直接复制给 OpenCode 的指令
你现在要基于已有的技术设计文档，先实现一个最小可运行原型，用于验证“项目蓝图可视化系统”的可行性。

不要一次性实现完整系统。
当前阶段只做 MVP，目标是跑通一条最小闭环：

指定本地项目目录 → 扫描 Python 文件 → 读取 Git 提交记录 → 生成蓝图节点和关系 → 前端无限画布展示。

### 一、当前 MVP 范围

后端需要实现：

1. 接收一个本地项目目录路径
2. 校验该目录是否存在
3. 校验该目录中是否包含 .git 目录
4. 递归扫描该目录下的 .py 文件
5. 为每个 Python 文件生成一个节点
6. 读取 Git log，提取每个文件的最近一次提交时间
7. 根据最近提交时间判断节点颜色：
   - 7天内提交：近期提交
   - 7天前提交：较早提交
   - 没有 Git 提交记录：未提交
8. 如果两个 Python 文件之间存在 import 关系，则生成一条连线
9. import 关系只做基础识别即可，不需要做到完全精确
10. 返回 JSON 格式的蓝图数据给前端

前端需要实现：

1. 使用无限画布展示蓝图
2. 节点使用“圆圈 + 文字”形式，类似游戏科技树
3. 鼠标悬停节点时显示详细信息，包括：
   - 文件路径
   - 最近提交时间
   - 提交 hash
   - 提交信息
   - 节点状态
4. 节点按 Git 提交时间区分颜色
5. 支持缩放、拖拽、平移
6. 支持按文件名或路径搜索节点
7. 支持点击某个节点后高亮它的上下游关系

### 二、前后端职责划分

后端职责：

- 项目目录扫描
- Python 文件发现
- Git log 读取
- import 关系解析
- 节点状态计算
- 返回结构化蓝图数据

前端职责：

- 无限画布渲染
- 节点展示
- 连线展示
- 悬停详情
- 搜索
- 高亮上下游
- 颜色区分新旧提交

前端不直接读取本地项目目录，也不直接执行 git 命令。
所有项目数据都通过后端接口获取。

### 三、最小接口设计

后端至少提供一个接口：

POST /api/blueprint/scan

请求体：

{
  "project_path": "本地项目目录路径"
}

响应体：

{
  "project_path": "...",
  "generated_at": "...",
  "nodes": [
    {
      "id": "唯一节点ID",
      "label": "显示名称",
      "file_path": "相对路径",
      "absolute_path": "绝对路径",
      "last_commit_time": "最近提交时间",
      "last_commit_hash": "提交hash",
      "last_commit_message": "提交信息",
      "status": "recent | old | uncommitted",
      "module_name": "模块名",
      "functions": ["函数名列表"]
    }
  ],
  "edges": [
    {
      "source": "来源节点ID",
      "target": "目标节点ID",
      "relation": "import"
    }
  ]
}
四、节点生成规则
每个 Python 文件生成一个节点。
节点 ID 建议使用文件相对于项目根目录的路径，例如：
perception/detection/object_detector.py
节点显示名称使用文件名，例如：
object_detector.py
悬停详情中显示完整相对路径。
五、连线生成规则
如果文件 A 中 import 了文件 B 对应的模块，则生成一条边：
A -> B
当前阶段只需要做基础 import 识别，不需要处理所有复杂情况。
需要识别：
import xxx
from xxx import yyy
from xxx.yyy import zzz
不需要一开始处理：
?动态 import
?条件 import
?第三方库 import
?复杂别名解析
?循环 import 的完整分析
第三方库节点可以先忽略，只保留项目内部 Python 文件之间的关系。
六、Git 记录处理规则
后端需要进入指定项目目录后执行类似逻辑：
git log --pretty=format:"%H|%aI|%s" -1 -- "文件路径"
如果文件有提交记录，则取最近一次提交时间。
如果文件没有提交记录，则标记为：
uncommitted
颜色规则：
状态	含义	颜色
recent	7天内提交	亮绿色
old	7天前提交	灰色
uncommitted	无提交记录	蓝色
七、前端节点样式
节点使用圆圈节点。
节点内部显示：
文件名
例如：
object_detector.py
如果文件名太长，可以截断显示，例如：
object_detec...
鼠标悬停时显示完整信息。
节点样式建议：
?圆圈外形
?中心显示文件名
?边框颜色表示提交状态
?悬停时弹出详情浮层
?选中时高亮节点和连线

九、验收标准
MVP 完成后，必须满足以下验收标准：
1.可以输入一个本地项目目录路径
2.后端能成功扫描该项目中的 Python 文件
3.后端能读取该项目的 Git 提交记录
4.前端能展示无限画布
5.每个 Python 文件都能显示为一个圆圈节点
6.节点之间有 import 关系时能显示连线
7.鼠标悬停节点时能显示文件路径、最近提交时间、提交信息
8.节点能根据最近提交时间显示不同颜色
9.7天内提交、7天前提交、未提交三种状态能明显区分
10.系统能稳定运行，不会因为单个文件解析失败而整体崩溃
十、错误处理要求
后端必须做基础错误处理：
1.项目路径不存在时返回明确错误
2.项目路径不是目录时返回明确错误
3.目录中没有 .git 时返回明确错误
4.某个 Python 文件无法解析时，跳过该文件并记录日志，不中断整体扫描
5.Git 命令失败时返回明确错误
6.前端请求失败时显示错误提示，而不是白屏
十一、实现顺序
请按以下顺序实现：
1.后端先实现项目目录校验
2.实现 Python 文件扫描
3.实现 Git log 读取
4.实现基础 import 解析
5.组装成节点和边
6.提供 /api/blueprint/scan 接口
7.前端先实现无限画布
8.实现圆圈节点
9.实现悬停详情
10.实现颜色区分
11.实现搜索和上下游高亮
十二、禁止事项
当前阶段不要做：
?不要引入复杂权限系统
?不要做完整 CI/CD 集成
?不要做真实测试框架数据接入
?不要做复杂类型推断
?不要做完整代码语义分析
?不要做生产部署
?不要过早优化性能
?不要把 MVP 写成完整产品
当前目标不是完成完整系统，而是先验证：
“后端扫描项目目录 + Git 记录 → 生成蓝图数据 → 前端无限画布展示”这条链路是否可行。
