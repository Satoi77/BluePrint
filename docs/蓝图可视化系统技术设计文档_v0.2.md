## 1. 项目概述

### 1.1 背景

当前机器人大脑项目已积累超过 13 万行代码、近 800 个 Python 文件，项目结构呈现多层嵌套、网状依赖、积木式拼接的复杂特征。项目包含工作流程管道、训练管线、素材管理、Demo 场景、子项目拼接等多个维度，传统 Git 文件版本管理系统完全无法理解项目结构语义。

目前项目管理主要依赖开发者的个人记忆力，随着项目规模持续增长，出现以下痛点：

- 无法直观了解项目整体结构和各模块状态
- 修改一个模块后，难以判断对下游依赖的影响范围
- 孤立功能模块缺乏统一管理，容易遗忘或重复建设
- AI Agent 编程时缺乏项目"世界观"上下文

### 1.2 系统目标

构建一套**蓝图可视化系统**，实现：

1. **全自动项目发现**：系统启动时仅需指定项目根目录路径，自动递归扫描 Python 文件结构，自动定位并解析 .git 目录获取完整提交历史，无需任何 block.yaml 或手动配置文件。
2. **本地轻量化运行**：完全本地部署，个人使用。后端 uvicorn + 前端 npm run dev，无 Docker、无 Nginx、无服务器依赖。
3. **增量更新与历史追溯**：基于 Git Hook 触发增量更新蓝图；通过颜色区分新旧提交（7天内提交绿色高亮，7天前提交灰色），并在节点上显示最近提交时间戳。
4. **健康度 Mock 机制**：测试阶段及默认状态下，健康度数据使用 Mock 填充，真实数据接入由用户后续自行扩展，系统不阻塞主流程。
5. **极简端口匹配**：端口连接校验采用字符串名称匹配（String Name Match），不进行严格的类型系统检查，确保"能用就行"，降低接入成本。

### 1.3 非目标

1. **不管理 block.yaml**：系统不读取、不生成、不校验任何手动维护的积木配置文件，完全依赖代码静态分析与 Git 历史。
2. **不做版本对比功能**：不提供两个 Commit 之间的 Diff 对比视图，仅通过颜色和时间戳在单视图中体现变更状态。
3. **不做严格类型检查**：不实现类似 Rust/TypeScript 的端口类型推导与校验，避免过度设计。
4. **不做远程部署**：不提供 Dockerfile、K8s Manifest 或 Nginx 配置，不支持多用户并发权限管理。
5. **不做 CI/CD 集成**：不主动推送到外部系统，仅被动监听本地 Git Hook 或轮询。

## 2. 设计思路

### 2.1 核心理念

**"代码即蓝图，Git 即时间轴"**。系统不创造任何元数据，所有节点、边、状态均源自代码文件的 Import 关系与 Git 提交记录。可视化只是对现有工程事实的实时映射。

Git 继续做它擅长的事（文件版本管理），蓝图系统做 Git 做不了的事（项目结构理解）。两者互补，而非替代。

### 2.2 蓝图驱动方式

采用 **"AI 建图 + Git 增量维护"** 的双驱动模式：

| 阶段 | 驱动者 | 职责 |
|------|--------|------|
| 首次建图 | AI Agent（OpenCode） | 全量扫描代码库，理解语义，生成蓝图初稿 |
| 增量更新 | Git Hook | 每次提交后，仅分析变更文件，局部更新蓝图 |
| 人工校正 | 开发者 | 修正 AI 判断错误，调整归属/连线/分类 |

**时序 rationale**：蓝图早期不完善，若一开始让 Git 驱动，新节点找不到归属位置。AI Agent 具备语义理解能力，适合首次全量建图；待蓝图基准稳定后，Git Hook 的轻量增量更新成本更低。

**冷启动流程**：

1. 用户指定项目路径
2. ProjectScanner 递归扫描 .py 文件
3. GitLogParser 读取 .git 历史
4. DependencyBuilder 构建全量图
5. 前端渲染

**热更新流程**：

- **方式 A（推荐）**：本地 Git Hook（post-commit）触发 HTTP Webhook → 后端增量解析最新 Commit → 推送 WebSocket 更新
- **方式 B（兜底）**：前端定时轮询 /api/status → 后端对比本地 Git HEAD → 若有变更则增量更新

**数据源**：

- **结构**：AST 分析 import 语句
- **状态**：Git Commit Timestamp + 文件变更列表
- **健康度**：Mock 随机生成或固定值

### 2.3 节点拓扑分类

受游戏科技树（如育碧纪元系列）启发，节点分为三种拓扑类型：

| 类型 | 说明 | 可视化表现 |
|------|------|-----------|
| Connected（链式） | 主线流程中的核心模块，有明确的上下游依赖 | 主画布中实线连接 |
| Branch（分支） | 从主线分出的可选功能分支 | 主画布中实线连接，视觉区分 |
| Isolated（孤立） | 独立功能，不与主线直接连接 | 孤立节点池面板，支持拖拽接入 |

系统自动将节点分为三类，并在 UI 上分区或分层展示：

1. **Connected（核心）**：入度或出度 > 0，属于主依赖链
2. **Branch（分支）**：仅被单一模块引用，或仅引用单一模块，属于功能分支
3. **Isolated（孤立）**：入度 = 0 且 出度 = 0，可能是废弃代码、脚本入口或测试文件，收入孤立节点池

### 2.4 LOD 分层渲染策略

| 级别 | 触发条件 | 渲染内容 | 交互 |
|------|---------|---------|------|
| L0 | 全局概览 / 缩放 < 0.3 | 仅显示分组边界框 + 组名 | 点击跳转 |
| L1 | 缩放 0.3 - 0.6 | 圆圈 + 模块名（截断） | 悬停显示 Tooltip |
| L2 | 缩放 0.6 - 1.2 | 圆圈 + 完整名 + 端口 + 状态色 | 拖拽、连线 |
| L3 | 缩放 > 1.2 / 选中 | 完整卡片 + 代码预览 + 提交详情 | 编辑、跳转 IDE |

**关键约束**：任何时刻屏幕上可见节点不超过 30-50 个。L3 不展开到画布上，用侧边面板展示。

### 2.5 自动发现机制

**替代原有的"积木注册表"机制**：

1. **文件扫描**：os.walk 遍历目录，跳过 __pycache__、.venv、tests（可选）
2. **模块识别**：
   - 每个 .py 文件 = 1 个潜在节点
   - __init__.py 存在 = 目录即模块（Package）
   - 类/函数装饰器 @block（若存在）= 显式标记，否则按文件粒度
3. **依赖提取**：使用 ast 模块解析 import X 和 from X import Y，映射为有向边
4. **Git 关联**：
   - 执行 git log --name-status --pretty=format:"%H|%ai|%s"
   - 建立 FilePath -> [CommitHash, Timestamp] 映射
   - 计算 is_recent：(Now - Timestamp) < 7 days（可配置）

### 5.2 核心模块设计

#### 5.2.1 项目目录扫描器（project_scanner.py）

职责：递归扫描项目目录，解析 Python 文件结构。

- **输入**：root_path: str
- **逻辑**：
  1. os.walk(root_path)，跳过 .git、__pycache__、.venv
  2. 对每个 .py 文件，使用 ast.parse 提取 Import 和 ImportFrom
  3. 记录：file_path、module_name、imports: List[str]、classes: List[str]
- **输出**：List[FileMeta]

#### 5.2.2 Git 日志解析器（git_log_parser.py）

职责：读取 Git 仓库历史，建立文件到提交的映射。

- **输入**：repo_path: str
- **逻辑**：
  1. 使用 git.Repo(repo_path) 自动发现 .git
  2. 执行 repo.iter_commits('HEAD', max_count=1000)（可配置）
  3. 对每个 Commit，提取 committed_date、message、stats.files
  4. 构建 file_to_commits: Dict[str, List[CommitInfo]]
- **输出**：GitHistory（包含文件到提交时间的映射）

#### 5.2.3 依赖图构建器（dep_builder.py）

职责：基于扫描结果和 Git 历史，构建蓝图有向图。

- **输入**：List[FileMeta], GitHistory
- **逻辑**：
  1. 创建节点：id=module_name, label=file_name, ports=[...]
  2. 创建边：遍历 imports，若目标模块存在，则 add_edge(src, dst, port_name=import_name)
  3. **端口匹配**：if src_port.name == dst_port.name: connect()（字符串名称匹配）
  4. 注入 Git 状态：node.data.last_commit = history.get(file_path)
  5. 计算孤立节点：if in_degree == 0 and out_degree == 0: mark_isolated()
- **输出**：BlueprintGraph（Nodes + Edges）

#### 5.2.4 状态聚合器（mock_health.py）

职责：为每个节点生成 Mock 健康度数据。

- **逻辑**：
  - 基于 node_id hash 保证同一节点健康度稳定
  - seed = hash(node_id) % 1000
  - random.seed(seed)
  - return round(random.uniform(0.6, 1.0), 2)
- **输出**：float（0.0 - 1.0）

#### 5.2.5 Git Hook 处理器

- **文件**：hooks/post-commit
- **内容**：
  ```bash
  #!/bin/sh
  curl -X POST http://localhost:8000/api/internal/git-hook \
       -H "Content-Type: application/json" \
       -d '{"event": "post-commit"}' &
  ```
- **后端处理**：收到请求 -> git_log_parser.parse_incremental() -> graph_store.update() -> ws.broadcast()

#### 5.2.6 AI Agent 适配器（简化）

- **现状**：暂不实现
- **理由**：AST + Git 已足够构建结构图。AI 仅在未来需要"自动补全注释"或"智能聚类"时接入。当前版本保持纯规则驱动。

### 5.3 Git 集成方案

1. **自动发现**：git.Repo(path, search_parent_directories=True)
2. **无侵入**：不修改用户 .git/config，仅读取对象
3. **Hook 安装**：提供 python -m backend.install_hook <project_path> 命令，自动将 post-commit 脚本复制到 .git/hooks/ 并 chmod +x

**外观**：

- **L1/L2**：`<div className="w-10 h-10 rounded-full border-2 flex items-center justify-center text-xs">`
- **文字**：节点下方绝对定位，text-ellipsis
- **端口**：左侧 Input，右侧 Output，圆形小点

**交互**：

- **Hover**：显示 Tooltip（Commit: 2026-09-12, Health: 0.95）
- **Click**：右侧 DetailPanel 展开，显示完整 Commit Message、文件路径、健康度趋势图（Mock）

### 6.4 LOD 分层实现

- **监听**：onMoveEnd -> const zoom = viewport.zoom
- **策略**：
  - zoom < 0.3: 隐藏所有 Node，仅显示 GroupNode（L0）
  - 0.3 <= zoom < 0.6: 显示 CircleNode（L1），隐藏端口，隐藏 Label 细节
  - zoom >= 0.6: 显示 FullNode（L2/L3），渲染端口、完整 Label、状态徽章
- **优化**：使用 useMemo 缓存节点数据，避免 LOD 切换时重新创建 React 组件

### 6.5 孤立节点池设计

- **位置**：左侧固定侧边栏
- **数据源**：nodes.filter(n => n.data.isIsolated)
- **交互**：
  - draggable={true}
  - onDragStart: 设置 dataTransfer 类型
  - Canvas onDrop: 创建新节点，位置为鼠标落点，保持孤立状态，除非用户手动连线

### 6.7 提交时间显示

每个节点需展示其最近一次 Git 提交的时间信息，帮助用户判断模块的活跃程度：

**显示位置**：

- 节点悬停 Tooltip 底部：显示 "Last Commit: 2026-09-12 14:30"
- 节点详情面板：显示完整的提交历史列表（最近10条）
- 节点圆圈边框颜色：根据提交时间自动着色（见 6.6 表）

**颜色区分规则**：

- 7天内有提交：节点边框使用亮绿色 #22c55e 高亮
- 7天前提交：节点边框使用灰色 #64748b
- 新文件（git add 但未 commit）：节点边框使用蓝色 #3b82f6
- 可配置阈值：通过 config.yaml 的 recent_days 参数调整

**时间格式化**：

- 相对时间：如"2小时前"、"3天前"（Tooltip 中显示）
- 绝对时间：如"2026-09-12 14:30:45"（详情页显示）

## 10. 风险与应对

### 10.1 技术风险

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| AST 解析不完整 | 依赖关系可能有遗漏 | 提供手动补充接口，允许用户手动添加边 |
| GitPython 兼容性 | 不同 Git 版本行为差异 | 同时支持 subprocess 调用 git 命令行作为降级方案 |
| 大规模节点渲染性能 | 800 节点可能卡顿 | LOD 裁剪 + 虚拟滚动 + WebGL 加速降级 |
| 循环依赖 | 图遍历可能死循环 | 检测循环依赖并标记警告，遍历加深度限制 |
| Mock 数据误导 | 用户可能误以为真实 | 明确标注"Mock 数据"水印，提供切换开关 |

### 10.2 工程风险

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 项目路径配置错误 | 扫描失败 | 启动时校验路径有效性，给出明确错误提示 |
| .git 目录缺失 | 无法读取历史 | 降级为"未提交"状态，不阻断扫描 |
| 大仓库 Git Log 慢 | 冷启动超时 | 分页读取 + 缓存 + 进度条提示 |
| 前端浏览器兼容 | 部分用户浏览器不支持 | 明确支持列表，提供降级提示 |

## 附录 A：MVP 最小系统验证指令

以下为可直接复制给 OpenCode 的指令，用于实现最小可运行原型：

### MVP 范围

后端需要实现：

1. 接收一个本地项目目录路径
2. 校验该目录是否存在
3. 校验该目录中是否包含 .git 目录
4. 递归扫描该目录下的 .py 文件
5. 为每个 Python 文件生成一个节点
6. 读取 Git log，提取每个文件的最近一次提交时间
7. 根据最近提交时间判断节点颜色：
   - 7天内提交：近期提交
   - 7天前提交：较早提交
   - 没有 Git 提交记录：未提交
8. 如果两个 Python 文件之间存在 import 关系，则生成一条连线
9. import 关系只做基础识别即可，不需要做到完全精确
10. 返回 JSON 格式的蓝图数据给前端

前端需要实现：

1. 使用无限画布展示蓝图
2. 节点使用"圆圈 + 文字"形式，类似游戏科技树
3. 鼠标悬停节点时显示详细信息，包括：文件路径、最近提交时间、提交 hash、提交信息、节点状态
4. 节点按 Git 提交时间区分颜色
5. 支持缩放、拖拽、平移
6. 支持按文件名或路径搜索节点
7. 支持点击某个节点后高亮它的上下游关系

### 最小接口设计

后端至少提供一个接口：

```
POST /api/blueprint/scan

请求体：
{
  "project_path": "本地项目目录路径"
}

响应体：
{
  "project_path": "...",
  "generated_at": "...",
  "nodes": [
    {
      "id": "唯一节点ID",
      "label": "显示名称",
      "file_path": "相对路径",
      "absolute_path": "绝对路径",
      "last_commit_time": "最近提交时间",
      "last_commit_hash": "提交hash",
      "last_commit_message": "提交信息",
      "status": "recent | old | uncommitted",
      "module_name": "模块名",
      "functions": ["函数名列表"]
    }
  ],
  "edges": [
    {
      "source": "来源节点ID",
      "target": "目标节点ID",
      "relation": "import"
    }
  ]
}
```

### MVP 验收标准

1. 可以输入一个本地项目目录路径
2. 后端能成功扫描该项目中的 Python 文件
3. 后端能读取该项目的 Git 提交记录
4. 前端能展示无限画布
5. 每个 Python 文件都能显示为一个圆圈节点
6. 节点之间有 import 关系时能显示连线
7. 鼠标悬停节点时能显示文件路径、最近提交时间、提交信息
8. 节点能根据最近提交时间显示不同颜色
9. 7天内提交、7天前提交、未提交三种状态能明显区分
10. 系统能稳定运行，不会因为单个文件解析失败而整体崩溃

### 实现顺序

1. 后端先实现项目目录校验
2. 实现 Python 文件扫描
3. 实现 Git log 读取
4. 实现基础 import 解析
5. 组装成节点和边
6. 提供 /api/blueprint/scan 接口
7. 前端先实现无限画布
8. 实现圆圈节点
9. 实现悬停详情
10. 实现颜色区分
11. 实现搜索和上下游高亮

### 禁止事项

当前阶段不要做：

- 不要引入复杂权限系统
- 不要做完整 CI/CD 集成
- 不要做真实测试框架数据接入
- 不要做复杂类型推断
- 不要做完整代码语义分析
- 不要做生产部署
- 不要过早优化性能
- 不要把 MVP 写成完整产品

当前目标不是完成完整系统，而是先验证：

"后端扫描项目目录 + Git 记录 -> 生成蓝图数据 -> 前端无限画布展示"这条链路是否可行。
