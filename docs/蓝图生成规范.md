# 蓝图生成规范（Agent 建图）

> 版本：v1.0 ｜ 日期：2026-09-13
> 定位：**功能结构图由 AI Agent 阅读代码后一次性生成；BluePrint 软件只负责导入、渲染与 Git 状态增强，不做语义分析。**

---

## 0. 为什么要 Agent 建图

静态分析（AST / import）只能得到"文件依赖"，得不到"业务功能"。用户要的是**功能层级**：
- 最底层 = **原子功能**（一个函数/类就是一个功能）；
- 多个函数可组成一个**常用功能**；
- 一条长链工作流也是一个功能；
- 最上层 = **业务大功能块**（如写小说软件的：生成素材 / 写正文 / 审核 / 提取信息）；
- 另有**孤立功能**（写公众号、设置、对话生成等待等）。

这类语义判断只有读代码的 Agent 能做。因此：

```
Agent 读代码  →  产出 blueprint.json  →  BluePrint 导入/渲染  →  Git 提供状态色（锦上添花）
```

Git 只回答"这块最近改没改"，不回答"这是什么功能"。功能结构是 Agent 的产物，一次建好，后续增量维护。

---

> **语言无关**：Agent 应收集项目**全部源码**（Python / JS / TS / Vue / React / Java / Go / C / C++ / C# / Rust / Shell 等任意语言），前后端同一业务归入同一大功能块。
> 完整可复制流程见项目 skill：`.opencode/skills/blueprint-generation/SKILL.md`。

## 1. 功能层级模型

| level | kind | 含义 | 示例 |
|-------|------|------|------|
| 0 | `block` | 业务大功能块 | 生成素材、写正文、审核、提取信息 |
| 1 | `group` | 大功能拆分出的子功能 | "章节正文生成"、"角色记忆维护" |
| 2 | `atomic` | 原子功能（函数/类） | `generate_chapter`、`audit_chapter` |

规则：
- 一个功能节点代表**一件事**，不是一个文件。**一个文件可以贡献多个功能，一个功能也可以跨多个文件**。
- 层级通常 3 层（0/1/2）足够；除非确有需要，不超过 4 层。
- 命名一律用**业务语言**（中文优先），不用文件名/技术名做功能名。文件与符号放进 `files`/`symbols` 字段。
- 判断"一个功能"的粒度：能独立描述其输入→输出、且能单独验收的最小能力。函数是原子；一组协作函数构成常用功能；跨多步的编排构成工作流功能。

## 2. blueprint.json 规范

```json
{
  "version": 1,
  "project_name": "novel_project_Web",
  "generated_by": "opencode agent",
  "generated_at": "2026-09-13T00:00:00Z",
  "functions": [
    {
      "id": "material",
      "name": "生成素材",
      "level": 0,
      "parent": null,
      "kind": "block",
      "description": "生成设定、卷纲、章纲等创作前置素材",
      "files": ["backend/app/routes/wizard.py", "backend/app/services/prompt_manager.py"],
      "symbols": ["run_wizard", "build_prompt"],
      "isolated": false
    },
    {
      "id": "material.chapter_outline",
      "name": "章纲生成",
      "level": 1,
      "parent": "material",
      "kind": "group",
      "description": "根据卷纲拆出每章要点",
      "files": ["backend/app/services/prompt_builder.py"],
      "symbols": ["build_chapter_outline_prompt"],
      "isolated": false
    },
    {
      "id": "write",
      "name": "写正文",
      "level": 0,
      "parent": null,
      "kind": "block",
      "description": "依据章纲逐章生成正文",
      "files": ["backend/app/routes/writing.py", "backend/app/services/novel_writer.py"],
      "symbols": [],
      "isolated": false
    },
    {
      "id": "settings",
      "name": "设置",
      "level": 0,
      "parent": null,
      "kind": "block",
      "description": "模型/密钥/系统参数配置",
      "files": ["backend/app/routes/config.py"],
      "symbols": [],
      "isolated": true
    }
  ],
  "edges": [
    { "source": "material", "target": "write", "type": "workflow", "label": "大纲→正文" },
    { "source": "write", "target": "audit", "type": "data", "label": "正文→审核" }
  ],
  "ignored": ["backend/tests/", "backend/scripts/", ".trae/"]
}
```

字段说明：

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | 是 | 全局唯一、稳定（建议 `block.sub.atomic` 点号路径）；不要用文件路径 |
| `name` | 是 | 业务名（中文优先） |
| `level` | 是 | 0/1/2 |
| `parent` | 是 | 父功能 id；L0 为 `null` |
| `kind` | 是 | `block` / `group` / `atomic` |
| `description` | 建议 | 一句话说明"做什么" |
| `files` | 建议 | 实现该功能的文件（相对项目根，POSIX 斜杠）。用于 Git 状态增强与定位 |
| `symbols` | 建议 | 关键函数/类名 |
| `isolated` | 否 | 是否为孤立功能（无依赖关系） |
| `edges[].type` | 否 | `workflow`（流程）/ `data`（数据流）/ `call`（调用）/ `import`（依赖） |
| `edges[].label` | 否 | 边上的文字说明 |
| `ignored` | 否 | 明确不纳入蓝图的路径前缀（测试、脚本、生成物等） |

## 3. Agent 生成流程（建议步骤）

1. **盘点结构**：列出目录树、入口点（`main`、路由注册、CLI、定时任务）、README/文档。
2. **识别大功能块（L0）**：从"用户能感知的业务能力"出发，例如：生成素材、写正文、审核、提取信息、写公众号、设置、对话生成等待。不要按技术分层（routes/services）命名。
3. **拆分功能（L1/L2）**：
   - 对每个 L0，读其入口函数，沿调用链向下追踪；
   - 把"独立可验收的能力"定为功能节点；
   - 到函数/类粒度即原子功能（L2）；
   - 一个函数若只是另一个功能的内部步骤，不要单独成节点（避免噪声）。
4. **建立关系边**：功能之间真实存在的数据流/调用/流程顺序才连边，并给 `type`/`label`。不要凭目录相邻乱连。
5. **标注孤立功能**：无任何上下游关系、独立成立的功能（设置、工具、独立入口）标记 `isolated: true`。
6. **映射文件与符号**：给每个功能填 `files`/`symbols`，便于软件定位与 Git 增强。
7. **覆盖校验**：项目内每个源文件要么被某个功能的 `files` 覆盖，要么在 `ignored` 中说明；不允许"下落不明"的文件（见 §4）。
8. **自检**：按 §5 清单逐条核对后输出。

---

## 4. 覆盖率与一致性要求（硬性）

- **文件覆盖**：所有源文件（排除 `ignored` 前缀、`.git`、`__pycache__`、`.venv`、`node_modules` 等）必须被至少一个功能的 `files` 引用。软件会计算覆盖率并报告未覆盖文件。
- **id 唯一**：`functions[].id` 全局唯一。
- **parent 合法**：每个非 L0 节点的 `parent` 必须存在于 `functions` 中，且 `parent.level === child.level - 1`。
- **level 与 kind 一致**：`0↔block`、`1↔group`、`2↔atomic`。
- **边端点存在**：`edges[].source/target` 必须是已定义的 `id`。
- **原子功能有落点**：`kind: "atomic"` 的节点应有 `symbols`（或 `files`）说明它对应哪段代码。

---

## 5. Agent 自检清单

- [ ] 顶层是**业务大功能块**，不是技术目录
- [ ] 功能名是业务语言，文件名只出现在 `files`
- [ ] 层级 ≤ 4，`level` 与 `parent` 自洽
- [ ] 原子功能到函数/类粒度，且不与父功能重复
- [ ] 边只连真实关系，带 `type` 与 `label`
- [ ] 孤立功能显式 `isolated: true`
- [ ] 文件覆盖完整（或已在 `ignored` 说明）
- [ ] JSON 通过 §2 schema，可被软件导入无报错

## 6. 给 Agent 的提示词模板（可直接复制）

```text
你是本项目的架构分析师。请阅读项目代码，产出一份"功能结构图" blueprint.json，
供 BluePrint 可视化系统导入。要求：

1. 以"业务功能"为单位，不要以文件/目录为单位。
2. 三层：L0 业务大功能块（如 生成素材/写正文/审核/提取信息）、L1 子功能、L2 原子功能（函数/类）。
3. 一个文件可贡献多个功能，一个功能可跨多个文件；用 files/symbols 字段映射到代码。
4. 只连真实存在的调用/数据流/流程关系，给 type 与 label。
5. 无依赖的独立功能（设置、工具、独立入口）标记 isolated: true。
6. 严格按 docs/蓝图生成规范.md §2 的 JSON schema 输出。
7. 自检 §4 覆盖率与一致性、§5 清单后再输出。
8. 只输出 blueprint.json 内容，不要额外解释。

项目根目录：<PROJECT_ROOT>
```

## 7. 软件侧（BluePrint）职责边界

| 软件做 | 软件不做 |
|--------|----------|
| 导入/校验 blueprint.json（schema、覆盖率、一致性） | 语义分析、判断"这是什么功能" |
| 渲染功能层级（LOD 语义缩放：L0→L1→L2） | 猜测功能归属 |
| Git 增强：按 `files` 聚合最近提交 → 状态色/时间 | 修改用户项目文件 |
| 孤立功能池展示 | |
| 未覆盖文件、缺失 parent 等报告 | |

后续增量（锦上添花）：Git commit 后，按变更文件定位受影响的功能节点，提示 Agent 局部复核，而非软件自动改功能结构。
